# FraudPulse behavioral risk research specification

## Financial question and roles
Finance: minimize missed transaction losses and unnecessary investigations rather than maximize accuracy. Quant/ML: fit transparent logistic regression on historical behavior, keep preprocessing train-only, choose a threshold on validation cost, and report untouched chronological test outcomes. Data: validate user CSV, require UTC timestamps, account identifiers, one reporting currency, positive finite amounts and binary settled labels. Software: preserve the Express/Prisma/BullMQ operational product and add an independent FastAPI research endpoint consumed through a Next server proxy. UI: lead with review burden and missed loss; expose ROC/PR, threshold comparisons and per-transaction contributions. Release: pinned installs, meaningful unit/integration/UI smoke coverage, lint/type/build and remote CI. Independent review belongs to the portfolio orchestrator.

## Approach and alternatives
Add a research workflow to the existing ML service and dashboard, avoiding a new service or infrastructure dependency. Replacing operational scoring would create unsafe deployment assumptions; a notebook-only study would prevent real input-driven use. Research scoring uses amount deviation relative to an account's prior 30-day behavior, prior one-hour velocity, prior category novelty, country switches and UTC-hour novelty. No label is a feature. Equal timestamps are scored before any of their observations update state. Cold starts are explicit; geography is a country transition signal, not impossible-travel proof.

Train/validation/test use whole timestamp groups, approximately 60/20/20. Validation picks cost = review_cost × flagged + false_positive_cost × false_positives + loss_fraction × missed_fraud_amount. Test metrics include confusion matrix, precision/recall, ROC-AUC, trapezoidal PR-AUC and average precision, alongside always-allow and always-review baselines. Costs are scenario assumptions, not realized savings. A deterministic DEMO DATA fixture illustrates the workflow without claims of real-world model performance. User imports never fall back to it after errors.

## Acceptance
CSV uploads and JSON API work without Postgres/Redis; malformed timestamps, NaN, duplicate transaction IDs, mixed currency and one-class training samples fail clearly. Future/same-time observations cannot change earlier features; test labels cannot affect fit or threshold. Explain individual flagged transactions through signed logistic log-odds contributions and observed behavioral values. Preserve repository, visibility and prior history. Production authentication, label-maturity ingestion, model deployment/calibration and streaming behavioral state remain explicitly outside this research release.
